# Mission — AI native 设计系统

> 状态：草案 v0.1 · 最后更新 2026-11-14
> 本文件定义「为什么做」，是其他所有 spec 的最高约束。与本文冲突的 spec 一律作废。

## 1. 一句话使命

把视觉规范从「设计稿里的像素」变成「机器可读、可校验的唯一事实源」，代码化设计系统，目标是搭建可被AI直接调用、可import复用的组件与token规范，让 AI 和人使用同一套 token 与组件产出视觉一致的页面。

## 2. 要解决的问题

现状的痛点是**规范在传递中必然失真**：

| 环节 | 现状 | 结果 |
| --- | --- | --- |
| 设计 → 开发 | 靠人肉对照设计稿还原 | 颜色/间距逐像素漂移，改一处漏三处 |
| 设计 → AI | AI 只能靠猜「什么红叫主色」 | 产出的页面看起来「像但不统一」 |
| 改版 | 值散落在多个文件 | 无法确认是否改全，只能靠肉眼扫 |
| 多品牌/多主题 | 每套主题单独维护 | 组合数一多就失控 |

根因不是工具，而是**没有单一事实源，也没有可执行的校验**。

## 3. 使用者

| 优先级 | 使用者 | 使用方式 |
| --- | --- | --- |
| P0 | 我（设计师） | 改 token、定规范、验收页面 |
| P0 | AI Agent | 读 `registry.json` + `AGENTS.md` + 解析后的 token 直接组装页面 |
| P1 | 协作前端 | 按组件规范接入，不重定义样式 |

由此得出第一条设计取向：**为 AI 可读性做优化，不等于牺牲人的可读性，但两者冲突时优先 AI**（例如 token 名宁长不缩写）。

## 4. 目标（首版）

1. token 源文件只用 `oklch`，一条命令产出可直接消费的 CSS 变量与 JSON。
2. 主题与品牌通过 modifier 组合，不复制文件；CSS 产物为 `2 + N` 份。
3. 组件带机器可读元数据，聚合为固定排序的 `registry.json`，可被 AI 或脚本消费。
4. 文档站所有值从解析结果读取，站内零硬编码样式值。
5. 关键约束由 CI 强制（hex 快照、色域、registry 漂移），不依赖人记得。

## 5. 非目标（明确不做）

- **不做移动端 / 原生端 token 输出**：首批消费方只有 Web。多端是后续彼此独立的新功能，不预留抽象层。
- **不做设计稿自动解析**：不从 Figma 反向生成 token。
- **不做对外开源的治理体系**：无贡献指南、无社区流程、无多团队版本协商。
- **不做「像素级还原」工具**：目标是结构与取值一致，不做视觉回归的逐像素比对。
- **不追求 token 全覆盖**：只覆盖实际用到的语义层，不做「完备设计体系」的学术完整性。

## 6. 成功标准（可判定）

| 标准 | 判定方式 |
| --- | --- |
| AI 零歧义产页 | 只给 spec + registry，AI 产出的页面不需要人工改颜色或间距 |
| 单点生效 | 改一个 token 值，文档站与页面同步变化，`grep` 无硬编码残留 |
| 主题可验证 | 切换 theme / brand 后能立即看到对应 CSS 输出，且不支持的模式被禁用 |
| 约束可执行 | 故意违反（写 hex、改 registry 不同步）时 CI 会失败 |

## 7. 设计原则

1. **单一事实源**：值只允许在一个地方定义，其余全部引用。
2. **token 是公共 API**：命名即契约，改名是破坏性变更，需 semver 与 `$deprecated`。
3. **能编译校验的，不写成文档要求**：规则优先落成 lint / test / CI。
4. **结构性一致性 > 灵活性**：宁可少一个可选项，也不允许出现两种写法。
5. **渐进交付**：每个阶段都有可验收的独立成果，不追求一次性完整。
