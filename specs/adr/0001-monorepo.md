# ADR-0001 采用单仓多包（monorepo）而非多仓

- 状态：Accepted
- 决策日期：2026-11-14
- 记录日期：2026-11-15
- 决策者：项目所有者
- 取代：无

## 背景

`packages/tokens`（token 源与产物）、`packages/ui`（组件与 `registry.json`）、`apps/docs`（文档站）之间存在单向强耦合：

- 改一个 token 通常要同步改组件引用与文档站展示。
- `registry.json` 生成后提交，必须与组件代码同版本可追溯（CI 用 `git diff --exit-code` 防漂移）。
- 文档站是验收台，且自身用本套 token 构建——验收台与被验收对象必须同版本。
- P0 使用者包含 AI Agent，其工作方式是读文件：`AGENTS.md` + `specs/` + `registry.json` + token 需要可一次性取得。

初始倾向为分仓（token 一仓、组件库一仓），理由是组织边界更清晰。经讨论后改变。

## 备选方案

**A. 多仓**：tokens / ui / docs 各一仓，跨仓以发布物消费。

**B. 单仓多包**：一个仓库，三个独立包（各自 `package.json` / 版本号 / 测试），`workspace:*` 引用。

**C. 单包扁平**：一个仓库、一个包，`src/{tokens,components,sections}` 平铺，无包边界（在 S1 规格对齐阶段评估过）。

## 决策

采用 **B. 单仓多包**，并严格保持包边界。

“同仓”不等于“同包”：包边界负责清晰度，仓库数量不负责。消费方仍可单独安装 `@ds/tokens`，体验与分仓一致。

C 未被采纳：单包没有包边界，`files` / `exports` 不成立，token 无法被外部仓库消费，会在 S3 前后堵死“他人用这套东西做 vibe coding”的路径。

## 理由

1. **原子变更（决定性）**。破坏性改名时，多仓存在版本窗口：tokens 已发大版本、ui 尚未升级，此时安装「最新 tokens + 最新 ui」即为损坏状态；且三个 PR 需按序合并、组合 CI 无人验证。单仓是一次分支、一次 CI、一次合并。对“AI 直接 commit”尤为关键——不能要求 agent 正确操作三个仓库并按序发三个版本。
2. **端到端校验可落在一条流水线**。校验链跨越三个包：token 合法性 → CSS 变量完整性 → 组件无硬编码 → 文档站色板一致 → 主题无漏映射。
3. **AI 上下文成本最低**。一次 checkout 即可取得全部规则、规格与产物索引；分仓时任一仓库规则漏读都会导致改错。
4. **可逆且低后悔**。先同仓、严格包边界，将来需要拆分时可用 `git filter-repo` 连历史抽出单个包；反向（先分仓后合并）需处理两套历史、CI 与发布配置。

判断标准可压缩为一句：**改一次 token，需不需要同时改组件和文档？** 需要即应同仓。

## 后果

正向：

- 跨包改动可原子提交与回滚，不存在版本窗口。
- 一条 CI 覆盖全链路约束，治理（semver / changelog / 门禁）只需一套工具链。
- 规格、组件、文档同仓，`grep` 一次全局命中。

负向（需承担的成本）：

- CI 成本随包数增长，必须用 `--filter` 控制。
- 版本节奏被绑定，独立发版需 changesets 之类工具。
- 权限只能到仓库级，无法单独授权 tokens 目录。
- 技术栈统一，单个包换框架或换包管理器的阻力变大。
- 多人并行时 `pnpm-lock.yaml` 容易冲突。

## 重新评估的触发条件

满足任意两条即重新评估拆分（新写一条 ADR 取代本记录，不修改本条）：

1. 出现只要 token、不要组件的独立消费方（iOS / Android / 小程序）。
2. token 与组件由不同团队维护，发布节奏不同。
3. 存在硬性权限隔离要求（如外部合作方只可读 token）。
4. 仓库规模明显影响 clone、CI 或 IDE 索引速度。

补充：业务消费方本来就在其他仓库。本 ADR 的范围是「设计系统自身」，S4 的跨仓变更通知与升级 PR 属于对下游消费方的治理，不构成拆仓理由。
