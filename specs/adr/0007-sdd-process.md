# ADR-0007 采用 SDD 流程与规格生命周期

- 状态：Accepted
- 决策日期：2026-11-14
- 记录日期：2026-11-15
- 决策者：项目所有者
- 取代：无

## 背景

项目由设计师驱动、AI 执行。直接对话驱动的典型结果是：代码先于规格，三周后没人记得某个值为什么这么定；AI 每个会话重新猜一遍边界。

参考的是吴恩达的 Spec-Driven Development：**spec 是大脑，agent 是肌肉**。它不规定目录，只要求「规格先于代码、规格是唯一事实源、每个功能独立走一轮且验收可执行」。

## 备选方案

**A. 对话驱动**：想到哪写到哪，规格事后补或不补。

**B. 规格先行**：每个功能先写三件套，再实现，再按可执行清单验收。

**C. 重流程**：引入 RFC、评审会、多人签核。

## 决策

采用 **B**，并把以下约定固化下来：

- 宪法放 `specs/` 根：`mission.md`、`tech-stack.md`、`roadmap.md`，冲突时按此优先级。
- 功能规格放 `specs/<YYYY-MM-DD>-<kebab-case-功能名>/`，内含 `requirements.md`、`plan.md`、`validation.md`。
- 只用日期，不用序号；目录创建后不改名，范围变化改内容。
- 规格与代码同分支、同一次合并；合并后目录保留，作为决策历史。
- 计划、实现、验证分三个新会话，避免上下文污染。
- 需求变化先改 spec，再改代码。
- 阶段之间做重规划：小改动立即改宪法或规格，大改动记进 roadmap。
- 重复流程固化为 `.trae/skills/`，不单独维护 `prompts/` 目录。
- MVP 视为对 spec 的压力测试，不是交付节点。

## 理由

1. **可回溯**：三个月后出现可疑代码，顺着目录名能找回当时的需求、决策与验收标准。
2. **上下文边界**：一个功能目录就是一次功能循环的全部输入，AI 不必在多个文件间猜范围。
3. **验收可执行**：`validation.md` 里写不出命令或截图的条目，等于没有验收。
4. **AI 可替换**：规格在仓库里、用通用格式，换 IDE 或换 agent 不影响流程。

## 后果

- 每个功能多三份文档，且必须在实现前完成。
- 命令要写成 workspace 形式（如 `pnpm --filter @ds/tokens test`），不能用裸 `pnpm test`。
- 没有 spec 支撑的改动视为不合规，即使代码「看起来对」。
- 宪法允许写「待定」，但必须写清「什么时候定、依据什么定」。

## 重新评估的触发条件

1. 协作人数增加，需要正式 RFC 或多方评审。
2. 出现跨仓协同的功能，单一目录无法承载。
3. 实践发现三件套对某些小改动过重，需要定义「免规格改动」白名单。
